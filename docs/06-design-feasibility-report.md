# ReelReverse 设计提案可行性评估报告

> 评估对象：`docs/04-design-proposals.md`（v0.2，1018 行）  
> 评估日期：2026-11-25  
> 评估方式：文档审查 + 当前工作区代码静态核对  
> 结论：**有条件可行（Conditional Go）**

## 1. 执行结论

提案的产品方向与现有项目方向一致，12 项功能在技术上大多可以落地，但不能按原提案的路线图一次性开发。

当前建议不是简单的“可行”或“不可行”，而是：

1. **近期可以立即做**：智能快捷操作、成本粗估算、单租户镜头模板库。
2. **可以在完成前置验证后做**：单平台视频生成闭环、时间轴编辑、镜头向量检索、多模态融合。
3. **必须降级或暂缓**：AI 真伪检测只能作为“辅助报告”，不能作为法律取证结论；团队协作必须等待用户与权限体系重构。
4. **不能按原提案承诺工期**：详细方案合计约 85 人天，路线图合计约 73 人天，口径本身不一致；按当前代码基础重估约为 113–175 人天，且不含供应商接入等待、正式安全评估和长期运维。

### 1.1 推荐决策

- **批准 Phase 1**：低风险、可复用现有能力的功能立即启动。
- **Phase 2 先做技术验证，不直接承诺完整交付**：先确认一个视频生成平台的正式 API、测试账号和密钥方案。
- **Phase 3 延后**：向量检索、时间轴、多模态增强需要先明确数据量和存储方案。
- **Phase 4 单独立项**：团队协作本质上是认证、授权和多租户改造，不是 12 天的 UI 功能。
- **2.3 不作为近期 P0**：如果要做，只输出“AI 风格特征提示”，不输出确定性或法律意义上的真伪结论。

### 1.2 一句话判断

**产品方向可行，工程上必须先补基础设施、缩范围、分期交付；按原提案原样执行不可行。**

### 4.1 原提案工期口径问题

提案内部存在明显不一致：

- 详细方案合计约为 **85 人天**；路线图合计约为 **73 人天**。
- AI 真伪检测在详细方案写 15 天，路线图写 10 天。
- 配方执行在详细方案写 9 天，路线图写 5 天。
- 路线图新增“测试覆盖率提升”和“任务重试机制”，但前者不是一次性功能，后者在当前代码中已有重试基础设施。

因此，原路线图只能作为方向参考，不能直接作为项目排期或对外承诺。

## 5. 逐项可行性分析

### 5.1 镜头向量检索（2.1）

**结论：有条件可行，建议放在数据能力阶段，不建议作为第一个 P0。**

主要问题不是“能不能调用 CLIP”，而是数据一致性和检索质量：

1. 提案的数据模型写 `ARRAY(Float)`，而当前默认数据库是 SQLite，SQLite 不支持 PostgreSQL 的数组类型；提案同时推荐 Qdrant，导致关系数据库和向量库谁是真源不清楚。
2. 需要明确三选一：
   - PostgreSQL + pgvector：适合继续使用关系数据库并做过滤；
   - Qdrant：适合规模化向量检索，但增加部署、同步和备份成本；
   - SQLite + 本地暴力检索：适合小规模 MVP，不适合长期增长。
3. “文本查图片”需要处理中文查询。原始 CLIP 的中文文本编码能力有限，实际应评估多语言 CLIP、中文 CLIP 或先将查询规范化。
4. 关键帧更新、重分析、镜头拆分后，向量必须同步失效和重建；还要做 embedding 模型版本管理。
5. 检索效果不能只用“看起来相似”验收，需要准备查询集，评估 Top-K 命中率、重复率、延迟和人工满意度。

**建议：**先用本地暴力检索或 pgvector 做小规模 POC，达到一定镜头量后再引入 Qdrant。原 7 天仅够“能跑”，不够“可维护、可评估”。

### 5.2 时间轴交互编辑器（2.2）

**结论：可行，但必须按“编辑操作会触发重新分析”的完整链路设计。**

当前 `Shot` 已有起止时间，`app/api/routes.py:244` 也已支持编辑镜头属性，但没有边界编辑和拆分接口。时间轴不是简单的拖拽 UI：

1. 修改镜头边界后，需要重新计算中点、抽取关键帧、调用视觉模型重新分析，并重建 `video.md`/`video.json`。
2. 拆分镜头会新增 Shot，涉及镜头序号重排；`PromptShot.source_shot_index` 和已有 PromptPlan 的映射会失效。
3. 提示词项目版本不能静默覆盖；应保留旧版本，并把当前计划标记为“参考镜头已变化，需要重新生成”。
4. 长耗时操作应进入后台任务，前端通过 SSE 或轮询获取进度，不能在 PATCH 请求里同步完成。
5. 还要处理转录文本重新对齐，否则镜头字幕和镜头边界会出现错位。

**建议：**先做“只编辑属性”和“只读时间轴”，再做边界拖拽和拆分。原 10 天只能覆盖基础版，完整链路建议按 14–20 天评估。

### 5.3 AI 视频真伪检测报告（2.3）

**结论：作为“辅助审查报告”可行；作为媒体审核、版权纠纷、学术或合规取证结论不可行。**

当前 `ShotAnalysis.origin` 和 `confidence` 来自视觉模型对关键帧的分析，属于启发式判断，不是经过校准的取证概率。提案中的 82% 等数字如果直接展示，容易被误解为可复现的检测结论。

风险包括：

- 真实拍摄视频可能被误判为 AI；AI 视频也可能被漏判。
- 关键帧分析不能覆盖整段视频的时间一致性、音频伪造和元数据伪造。
- 不同生成模型、压缩、滤镜和二次剪辑会显著影响判断。
- “用于版权纠纷/合规审查”的表述需要法律和专业鉴定支持，不能仅凭模型输出。

**建议：**改名为“AI 风格特征提示”或“辅助信号报告”，输出证据、局限性和人工复核建议，不输出确定性法律结论；不要优先做 PDF 取证报告。若接入第三方检测服务，还需确认其授权、费用、数据留存和误差指标。

### 5.4 镜头模板库（2.4）

**结论：高可行、低风险，适合作为第一阶段功能。**

现有 `PromptShot` 已包含景别、运镜、主体、场景、光线、色调、Prompt 和负面词等字段，Entity Bible 和模型档位也可复用。模板库主要新增：

- 模板表：名称、描述、分类、标签、来源项目/镜头、模板 Prompt；
- 模板应用：把模板作为起点快照写入 PromptPlan，而不是在生成时动态引用；
- 搜索与筛选：分类、标签、模型档位；
- 权限归属：当前没有正式用户体系，第一阶段建议单租户，`owner_id` 可先留空或使用系统账号。

应用模板时要考虑镜头差异：直接把模板 Prompt 覆盖到所有镜头会破坏主体和动作一致性。更合理的是只填充风格、光线、运镜等可复用字段，再让生成器补全主体和动作。

**建议：**Phase 1 做单租户 5–8 天 MVP；多租户和团队共享等到认证体系完成后再做。

### 5.5 配方执行对接（2.5）

**结论：产品价值最高，也是风险最高的功能；必须单平台、先验证、后扩展。**

这是提案中最有价值的方向，因为它把“分析/提示词”变成真正的生产闭环。但当前设计有几个必须先修的硬问题：

1. **密钥安全**：`GenerationJob.api_config` 保存 API Key，接口参数直接接收 `api_key`，这会形成明文密钥落库、日志泄漏和前端回传风险。必须改成服务端 Secret Manager 或加密 `credential_ref`，永不把密钥返回前端，也不写入日志。
2. **供应商接口未验证**：提案中的 Kling 示例 URL、`self.api_key` 初始化、同步返回 `video_url` 都不能直接作为实现依据。真实平台通常是“提交任务 → 返回 task_id → 查询/回调 → 下载结果”的异步模型。
3. **适配器接口不完整**：`generate/status/format_prompt` 还不够，需要 `submit`、`poll`、`cancel`、`verify_callback`、`download_result`、幂等键、超时和错误分类。
4. **任务持久化**：当前后台任务依赖进程内线程，服务重启后任务可能丢失。生产级生成应使用持久化队列或带租约的数据库 worker。
5. **结果资产化**：平台返回的视频 URL 往往过期，必须下载到本项目存储，并记录 checksum、大小、格式和来源任务。
6. **多镜头一致性**：逐镜生成后还需要拼接、音频、转场、主体一致性和失败镜头补生成；这不是一个适配器就能解决。
7. **平台规则**：内容审核、版权、肖像权、商用授权、配额和计费都需要产品层处理。

**建议：**不要同时接 Kling/Runway/Pika。先选一个能拿到测试账号和正式文档的平台，完成“提交 → 查询 → 下载 → 本地保存 → 失败重试 → 费用展示”的 MVP。原 9 天不足以覆盖可靠接入，按 15–25 天评估。

### 5.6 多模态融合分析（3.1）

**结论：增量可行，但提案把“文本融合”和“真实音频理解”混在了一起。**

当前已有 ASR 转写，`app/services/fusion.py` 会把转录片段按时间区间附加到镜头；提示词生成也可以使用参考快照。可以先做低成本的文本融合：

- 将镜头视觉描述、转录文本、整体项目风格合并为上下文；
- 推断情绪、叙事角色和关键实体；
- 用融合结果增强 Prompt，而不是改变原始镜头事实。

真正的音频分析（情绪、乐器、节奏、音效）需要额外模型和音频数据，且要处理版权、噪声、方言和音乐识别误差。按“文本融合 MVP”4–6 天，按“真实音频情绪/乐器”10–15 天更合理。

### 5.7 离线模型模式（3.2）

**结论：代码层可行，部署层取决于硬件和客户环境。**

`LLMGateway` 已经集中管理模型选择，适合扩展 Ollama 或其他 OpenAI 兼容本地端点。需要补充：

- 本地模型服务地址、模型名、超时和健康检查；
- 视觉模型与文本模型分开配置；
- 本地 ASR（如 faster-whisper）；
- 模型不可用时回退云端或明确失败；
- 本地模型质量下降时的提示和对比。

代码适配约 5–8 天，但 GPU、显存、模型下载、升级和运维不属于“5 天功能”。如果目标客户有离线/隐私要求，这项值得做；否则不建议优先投入。

### 5.8 Redis 缓存（3.3）

**结论：有条件可行，原方案的缓存装饰器不能直接使用。**

提案用 `str(args)` 和 `str(kwargs)` 生成缓存键，这对包含 ORM 对象、模型实例、文件路径或不稳定字段的调用不可靠，容易缓存不命中或错误复用。必须改为：

- 规范化 JSON 输入；
- 内容哈希（图片/视频/文本）；
- 模型名、提示词版本、温度、档位、输出 schema 版本一起入键；
- 不缓存密钥、用户隐私和不可序列化对象；
- 有明确的 TTL、失效和清理策略；
- Redis 不可用时降级，不影响主流程。

基础缓存 4–6 天可行；完整版本化、监控和失效策略建议按 8–12 天评估。

### 5.9 智能快捷操作（4.1）

**结论：高可行，建议立即做。**

现有后端已经具备创建提示词项目、版本、对比、分享、导出和任务状态等能力。快捷操作主要是产品编排：

- 分析完成后一键生成复刻方案；
- 一键打开对比视图；
- 一键创建分享链接；
- 二维码需要额外前端或后端依赖，但不影响主流程。

3–5 天可以做出可用版本，是投入产出比最高的功能之一。

### 5.10 协作工作流（4.2）

**结论：方向合理，但当前不具备实施基础，建议暂缓。**

当前系统只有可选的全局 HTTP Basic Auth，没有 User、Team、TeamMember、项目归属和角色授权。提案中的 Team/TeamMember 也没有 `User` 表、邀请机制和项目关联。

真正落地至少需要：

1. 用户身份：OIDC/邮箱密码/会话或 JWT；
2. 团队与成员：邀请、角色、所有权转移；
3. 项目归属：Project、PromptProject、Job、Share 都要绑定 owner/team；
4. 全路由授权：不能只保护入口，还要防止通过 project_id、job_id、share token 越权；
5. 审计日志：谁改了什么、何时改的；
6. 数据迁移：已有匿名项目如何归属；
7. 安全测试：越权、枚举、分享链接和评论权限。

这不是 12 天能可靠完成的工作，建议按 25–40 人天单独立项。如果客户暂时只需要“分享给客户看”，现有分享链接比团队协作更优先。

### 5.11 分析质量仪表盘（5.1）

**结论：有条件可行，先补事件数据，再做图表。**

当前 `Shot` 只保存最新分析结果，`update_shot_analysis` 会覆盖 `analysis` JSON，没有完整的字段修正历史；因此“景别修正率、运镜修正率、来源修正率”不能可靠回溯。

需要先新增：

- 镜头编辑事件表（字段、旧值、新值、操作者、时间、来源）；
- 重分析事件和 Prompt 版本事件；
- 可选的少量人工标注/抽检结果；
- 指标口径和数据保留策略。

基础仪表盘 8–12 天；如果要做“准确率”而不只是“修正频率”，还需要人工标注和统计验证，不能只用系统内部数据宣称准确率。

### 5.12 成本监控（5.2）

**结论：可先做粗粒度，适合纳入 Phase 1。**

`LLMGateway.stats()` 已记录调用次数、输入 token 和输出 token，`Job.metrics` 也保存了这些数据；提示词项目也有 metrics。缺少的是：

- 模型价格表和生效日期；
- 按项目、任务、模型聚合；
- 图片/视频/ASR/生成任务的独立计费单位；
- 供应商实际账单对账；
- 汇率、折扣和套餐。

建议先明确显示“估算成本，不是账单金额”，并把价格表版本化。4–6 天可以做出可用的成本面板；精确账单需要供应商结算接口或人工对账。

## 6. 关键风险清单

| 风险 | 影响 | 建议 |
|---|---|---|
| 第三方视频生成 API 未核验 | 可能导致适配器返工、无法上线 | 先用测试账号完成接口 POC，再排开发 |
| API Key 明文存储或返回前端 | 严重安全事件 | 服务端 Secret Manager/加密引用，日志脱敏 |
| AI 真伪检测被当作法律结论 | 合规、声誉和客户纠纷 | 只做辅助报告，增加局限性和人工复核 |
| 向量存储与关系数据库双真源 | 数据不一致、维护成本高 | 先确定一种真源和同步策略 |
| 进程内后台任务重启丢失 | 生成任务卡死或重复扣费 | 持久化任务队列、幂等键和状态恢复 |
| 团队协作缺少授权模型 | 越权访问客户项目 | 先做认证与全路由授权，再谈协作 |
| 原工期低估 | 交付延期、质量下降 | 按重估区间排期，设置阶段门槛和缓冲 |
| 平台结果 URL 过期 | 用户无法回看生成视频 | 下载到自有存储并记录来源 |

## 7. 修正后的实施路线

### Phase 0：技术验证（3–5 天，建议先做）

- 选定一个视频生成平台，拿到正式 API 文档和测试账号。
- 验证鉴权、提交、轮询/回调、失败码、限流、结果下载和计费方式。
- 确定向量存储方案（pgvector / Qdrant / 本地索引）。
- 确定密钥管理和用户体系目标，不写死实现。

**门槛：**没有完成 API POC 和密钥方案，不进入 2.5 开发。

### Phase 1：低风险增强（约 2–3 周）

- 4.1 智能快捷操作（3–5 天）
- 5.2 成本粗估算（4–6 天）
- 2.4 单租户模板库（5–8 天）
- 同时补质量事件表的最小埋点，为 5.1 留数据

**目标：**让用户从“分析完成”更快走到“提示词复用”和“查看成本”，不引入高风险外部依赖。

### Phase 2：单平台生成闭环（约 3–5 周）

- 一个平台适配器（建议先选测试条件最好的平台，而不是一次接三家）。
- 服务端密钥引用，不存明文、不回传前端。
- 异步任务状态、超时、重试、幂等、结果下载和本地保存。
- 生成任务 UI、费用展示和失败原因。
- 如需要，再做多镜头拼接和一致性处理。

**目标：**跑通一个真实平台的最小闭环；多平台复制放到闭环验证之后。

### Phase 3：数据与编辑能力（按需求分轨，约 6–10 周）

不建议把以下四项同时开工：

- 2.1 向量检索（12–18 天）
- 2.2 时间轴编辑（14–20 天）
- 3.1 真实音频融合（10–15 天）
- 5.1 质量仪表盘（8–12 天）
- 3.3 缓存完整版（8–12 天）

**建议顺序：**先做能直接产生用户价值的时间轴或向量检索，再做缓存和仪表盘；离线模式只在明确客户需求出现时启动。

### Phase 4：协作与商业化（单独立项，25–40 天）

- 用户、团队、成员、角色、邀请。
- 项目归属和全路由授权。
- 审计、评论、审核流和数据迁移。
- 只有在认证体系完成后，才把 `user_id` 和团队共享接入模板库。

## 8. Go/No-Go 验收门槛

### 可以 Go

- 4.1 智能快捷操作：一键生成、对比、分享可在现有 API 上完成。
- 5.2 成本监控：能拿到 token 数据并明确标注估算口径。
- 2.4 单租户模板库：不影响现有匿名项目和生成流程。
- 3.2 离线模式的代码适配：有明确部署目标时再做。

### 条件 Go

- 2.5 配方执行：必须先完成平台 API 验证、密钥方案、异步任务和结果存储设计。
- 2.1 向量检索：必须先确定存储方案，并有至少一组可评估的查询集。
- 2.2 时间轴：必须先设计镜头版本映射和重分析任务。
- 3.1 多模态：先做文本/转录融合，真实音频分析单独评估。
- 3.3 缓存：先做内容哈希和版本化缓存键，再引入 Redis。
- 5.1 仪表盘：先补编辑事件，不要直接基于最新快照宣称准确率。

### 暂不 Go

- 2.3 取证级 AI 真伪检测：不能承诺准确率或法律用途。
- 4.2 团队协作：当前认证和授权基础不存在，12 天完成不现实。
- 多平台同时接入：先证明一个平台的完整闭环。

## 9. 最终建议

**是否可行：可行，但属于“有条件可行”。**

建议管理层或项目负责人做以下决策：

1. **立即批准 Phase 1**，用较低成本验证用户是否真的会使用模板、快捷操作和成本信息。
2. **把 2.5 配方执行定义为独立项目**，先做单平台 POC；没有供应商测试账号和密钥方案就不排开发。
3. **把 2.1、2.2 放入数据能力阶段**，先做存储和版本设计，不要按 7 天/10 天的乐观估算对外承诺。
4. **把 4.2 团队协作与认证重构绑定**，单独评估 25–40 天，不混在“体验优化”里。
5. **把 2.3 AI 检测降级为辅助功能**，避免把模型置信度包装成法律或审核结论。

如果只能做一件事，优先做 **单平台生成闭环（2.5）**，因为它最能验证“分析→生产”的产品价值；但必须先完成 Phase 0 的 API 与密钥验证。

如果必须在 2–3 周内交付，则只做 **4.1 + 5.2 + 2.4（单租户）**，不要同时启动向量检索、时间轴和团队协作。

---

**评估结论：Conditional Go。方向成立，原提案需要缩范围、补基础设施、重排优先级后才能进入开发。**
