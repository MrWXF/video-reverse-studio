# 02 规格、架构与计划

目标：把设计结论转成工程可执行的规格、架构边界、风险清单和测试计划，减少“开始很快、后期返工”的概率。

## 推荐组合

| 等级 | Skill | 主要用途 | 适用时机 |
| --- | --- | --- | --- |
| S | `spec` | 把模糊意图写成五阶段可执行规格 | 需求进入开发前 |
| S | `plan-eng-review` | 审查架构、数据流、边界条件与测试计划 | 技术方案评审 |
| A | `plan-devex-review` | 从开发者体验角度设计接入路径和首个成功时刻 | 平台、SDK、开放 API、内部工具 |
| A | `context-save` | 保存长任务的决策、进度和未完成项 | 上下文切换、跨天开发 |
| A | `context-restore` | 从保存点恢复任务上下文 | 新会话继续开发 |
| B | `autoplan` | 连续运行 CEO、设计、工程、DX 自动评审 | 成熟团队的大型计划 |
| B | `plan-tune` | 调整提问敏感度和开发者画像 | 个人长期使用 gstack |

## 逐项说明

### `spec`（S）

来源：gstack，`D:\project\github\gstack\spec\SKILL.md`。

用途：把模糊需求拆成范围、行为、接口、边界、验收标准和任务清单，必要时生成 issue 或 backlog 项。

适合：

- 需求只有一句自然语言描述；
- 多人协作需要统一理解；
- 需要把产品语言转成可测试的工程语言。

一份合格规格至少包含：

- 背景和非目标；
- 用户故事与主流程；
- 输入、输出、状态和错误；
- 数据模型与兼容性；
- 权限、安全和隐私；
- 性能与可观测性要求；
- 验收标准；
- 发布和回滚方案。

### `plan-eng-review`（S）

来源：gstack，`D:\project\github\gstack\plan-eng-review\SKILL.md`。

用途：以工程经理视角审查架构、数据流、依赖、失败模式、边界条件和测试计划，迫使隐藏假设显性化。

适合：

- 新服务、新数据模型、跨系统集成；
- 需要评估迁移和兼容成本；
- 计划看起来合理，但缺少失败路径和测试策略。

建议强制产出：

- 架构图和数据流；
- 关键依赖与降级策略；
- 幂等、并发、重试和超时；
- 数据迁移与回滚；
- 单元、集成、端到端和回归测试；
- 监控指标与告警阈值。

### `plan-devex-review`（A）

来源：gstack，`D:\project\github\gstack\plan-devex-review\SKILL.md`。

用途：模拟开发者角色，设计从发现产品到首次成功的路径，识别文档、认证、SDK、错误信息和调试体验中的摩擦。

适合开放 API、SDK、CLI、内部平台和需要外部集成的产品。纯终端用户产品可不作为必选。

配套的 `devex-review` 会在真实环境中走接入流程并计时，形成计划与现实的对照。

### `context-save` / `context-restore`（A）

来源：gstack，`D:\project\github\gstack\context-save\SKILL.md` 与 `context-restore\SKILL.md`。

用途：保存任务目标、已做决策、失败方案、剩余工作和关键文件；在新会话中恢复，减少重复探索。

注意：保存内容可能包含代码路径、业务信息和日志。不要把密钥、客户数据或完整生产日志写入上下文文件。

### `autoplan`（B）

来源：gstack，`D:\project\github\gstack\autoplan\SKILL.md`。

用途：顺序读取并运行 CEO、设计、工程、DX 四个评审 Skill，用固定原则自动决策。

适合大型版本或成熟流程；小改动会显得过重。自动决策不能替代产品负责人和技术负责人签字。

### `plan-tune`（B）

来源：gstack，`D:\project\github\gstack\plan-tune\SKILL.md`。

用途：记录开发者偏好，调整提问频率和敏感度。属于个人体验优化，不是工程治理能力。

## 计划阶段推荐流程

```text
设计文档 / 需求描述
  → spec
  → plan-eng-review
  → plan-devex-review（仅平台型产品）
  → 形成 ADR、任务拆分和测试计划
  → 进入开发
```

## 必须定义的工程约束

- 兼容范围：浏览器、系统、API 版本、数据格式；
- 性能预算：首屏、接口延迟、并发、成本；
- 可用性目标：错误率、重试、降级和恢复；
- 安全边界：认证、授权、输入校验、敏感数据；
- 可观测性：日志、指标、追踪、审计；
- 迁移策略：双写、回填、灰度、回滚；
- 测试策略：哪些用单元测试，哪些必须真实浏览器验证；
- 所有权：谁批准、谁发布、谁值班、谁回滚。

## 常见误区

- 规格只写 happy path，不写空状态、错误和权限；
- 架构评审只讨论技术选型，不讨论失败和迁移；
- 没有测试计划就进入开发，最后靠人工点击兜底；
- 把 Agent 的自动评审当作正式签字；
- 长任务不保存上下文，第二天重复调查同一问题。
